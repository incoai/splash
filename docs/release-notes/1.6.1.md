# Splash 1.6.1

Splash 1.6.1 keeps long prompts running at the memory limit, creates every prefill kernel before it says it is ready, runs faster on M5 and later Macs, keeps a server from stalling on its own console and its engine from stopping on a slow disk, and brings chat menus, PDFs and per-model updates and deletion to the Mac app.

## Memory

- **Spill lanes keep their pages while memory lasts** (#713). A lane's pages whose copies are on the SSD stay in memory until a claim needs them, then go, before any lane yields, so a Mac with room reads no KV back from the SSD.
- **A long prompt no longer fails partway through for want of memory the engine knew it lacked** (#713). A start that cannot spill starts in memory only where memory holds it now, waits for running lanes, or is refused at its start, with a message naming what it lacks. A prefilling lane can convert itself to Spill at the wall.
- **A lone request takes the whole context the server advertises** where the SSD cache cannot take its KV: its start is charged the buffers its lane takes, not the states its prefill may capture. On Flash-Next Q2_0 at `--max-memory 9.4G` with `--max-cache-disk 600M`, lone prompts of 60,000 and 65,497 of its 65,529 tokens complete. See [Upgrade](#upgrade).
- **Two long distinct requests at the memory limit complete where each does alone.** The one left alone when the other yields takes the pages the other left cached and its own whose copies are on the SSD, and fails with `capacity_exhausted` only once nothing else holds memory it could get: no cached page it may take, no write to the SSD on its way, and the expert store at its floor.
- **Critical pressure.** A lane's released extents pay for the Index runway's refill and its first reads, so a lane gives memory back under macOS's critical pressure and keeps running on the pages it has.
- **Flash-Next's PLE table streams on every Mac.** `--ple-memory auto` reads it through a row cache of at most 237 MiB, the rows a 128K-token prompt reads, rather than loading the 28.8 GB table on a Mac that holds it, and leaves that memory to the KV and its caches. See [Upgrade](#upgrade).
- `capacity_exhausted` names the lane's KV mode, phase and tokens, the Metal memory outside the engine's buffers, and the SSD cache only where the lane spilled.

## Speed

- On **M5 and later**, `--activations auto`, the default, rounds activations to int8 where that is faster: about a quarter less time to the first token on Qwen3.8-27B MLX 4-bit, 13–16% less time per decode cycle on Ternary-Bonsai, and 4–7% sooner first tokens at 32K–64K from attention over the INT8 KV cache. See [Upgrade](#upgrade) for what it costs in precision.
- **Streamed MoE** runs the resident experts' passes beside the load's host step: decode 8–17% faster on Flash-Next at 16G and 8G and on Qwen3.6-35B-A3B at 4G, without its 100–125 ms stalls.
- Attention at long context: time to first token 8% lower at 128K and 11–12.5% lower at 256K, long-context decode 2–6% lower. The last layer outputs only the rows something reads, prefill 1–2.3% lower. Smaller gains in the verify scan and on the 27B's decode.

## Fixes

- **A short request no longer hangs Apple9 GPUs of more than 10 cores** (#715). Every kernel a prefill chunk can run is created before Ready, and a fused projection is specialized to its dispatch's formats: 6–26 s of compiling on the serving thread becomes 0.1–2 s before Ready. A pipeline still created while serving is counted in `/status` under `metal.pipelines_created_while_serving`.
- **A long request no longer waits for a kernel the warm-up left out** (#736). The kernels of a decode past about 7,000 tokens, which scores INT8 queries on M5 and later, and of Flash-Next's sparse attention and PLE history are made before Ready too, where the first request to need each waited up to 0.1 s for it.
- **The first start after an update is faster and says how far its warm-up is.** It makes the GPU's programs four at a time, not one by one, and an MoE model's expert kernels only for the weight formats it uses: on a 48 GB M5 Pro, Flint starts in 22 s where it took 190 s, Flash-Next in 49 s (317 s), the 35B in 13 s and the 27B in 56 s (118 s); later starts take 6–15 s. The console counts the warm-up's steps, `Warming up · 3 of 11 steps`, and the app shows them as a bar on the Server screen, with a note on why the first start is slow.
- **A server whose engine has stopped for good exits** (#716), so that a supervisor can act on it. See [Upgrade](#upgrade).
- **A slow or sleeping disk no longer stops the engine.** A host step that worked past 5 s, such as an expert load or a spilled KV read from an external disk, failed its command with a GPU timeout and every request in flight with it: the work after a step now waits for it on the CPU. A weight restore after an idle release writes each image on a thread of its own, so a large one, such as Flash-Next's 28.8 GB PLE table under `--ple-memory off` from a disk slower than about 1 GB/s, no longer gets the engine restarted.
- **An engine failure at the memory limit, `unknown KV cache block`,** which failed every request in flight, is gone: a request waiting to start reads its cached prefix only as far as the cache still holds it.
- **A stalled console stalls nothing** (#719). One thread writes the console, the server's lines and the engine's, and no request or engine loop waits on it. Past 1,024 waiting lines it drops them, says how many and counts them in `/status` under `console.dropped_lines`.
- **A quarantine ends** (#717): a request in flight at two engine faults in a row is refused for an hour of awake time, no longer until the server restarts.
- **A client that vanishes frees its lane** (#718): a client that stops answering is dropped 60 s after its last data, through TCP keepalive.
- **Agents that interleave conversations** keep their tokenizer prefix: 16 prompts, one per conversation, instead of 4 (#721).
- **A request's claim met from cache, or waiting under a second, logs nothing** (#726), where a long reply at the memory limit logged a line per page.

## Mac app

- **Chat:** titles the model sums up; pinned chats and the others by day; a menu on each chat, and several chats deleted at once; PDFs attached in the app and the chat page; models started and switched from the composer; a message the server refuses goes back to the composer.
- **Models:** a menu on each model with a vision projector and a draft from this Mac, Check for Updates, and Delete. Start and switch models from the menu bar's panel. Only models this Splash can serve are offered; one a newer build put in the models folder stays hidden.
- **Server screen:** a row per request from its start to its end, a start's log kept across starts up to 8 MiB, and the start a failure says would fit. Context length offers 1M tokens for the models that serve it, and says that YaRN changes answers past the model's own window. The page scrolls below the toolbar's line, never under its buttons.
- Coding agents open in the drawer's terminals, in their folder. A quit asks first only where it would cut off work. The programs the app runs get the login shell's Hugging Face settings, read as the app launches, for at most 5 s.

## Upgrade

```bash
brew upgrade splash
```

Keep the CLI and desktop app on the same release.

- **Outputs differ from 1.6.0 on M5 and later.** `--activations auto` costs a next-token KL against bf16 of about 2.2e-3 on Qwen3.8-27B MLX 4-bit's prefill and 2.8e-4 on Bonsai's decode, and INT8 queries give 1.37x the KL the INT8 KV cache alone gives the 27B. `--activations bf16` keeps every activation bf16; a persistent cache keeps what an `auto` run prefilled, so a parity run starts in a fresh `--cache-dir`.
- **M3 and M4 Pro and Max GPUs of more than 10 cores** stage MoE experts, as every other GPU does, so a row's decode now depends on its batch.
- **Flash-Next's PLE table streams by default.** On a Mac that held it in memory, `--ple-memory off` keeps it there: a fresh prompt then reads none of its rows from the SSD, its first token 0.6 s sooner at 6K tokens on an M5 Pro.
- **Flash-Next's advertised context can be one KV extent shorter** (8,192 tokens at budgets near `--max-memory 9.4G`). It is the context a lone request takes: whole extents of KV beside the lane's state, the Index runway and the page tables of the spilled KV's readers, which a start that can spill holds from its start. Where the memory past the last whole extent was less than those, no lone request could take that extent, and it is no longer advertised.
- **Exit status 69** (`EX_UNAVAILABLE`): a server that stops restarting its engine now exits, where 1.6.0 stayed up answering 500. Requests until then get 500 `engine_failed`. A supervisor such as launchd with `KeepAlive` decides whether to start it again: give it a `ThrottleInterval` for a cause the next start meets again.
- **An update frees the earlier commit's Hub cache files** that nothing else links, unless another tool has downloaded into that snapshot. An older `--revision`, or a new commit that fails to load and needs the older one, downloads them again.
- **Log lines** of a request name it: `Done · request N · …`, one line for each request's end. Tools that parse them positionally need updating.
- **`/status`** keeps schema 8 and gains `console.dropped_lines`, `memory_governor.count_checks`, `metal.pipelines_created_while_serving`, `kv_spill.releases` and `released_pages`, and `tokenizer_cache.misses` and `evictions`. `/v1/models` gains `limits`.
- **The app's chats:** images move into attachment files of their own at the first launch. Chats written since are read by 1.6.0, but show their attachments only here.
- **GGUFs with a `general.alignment` below 8** are refused.
